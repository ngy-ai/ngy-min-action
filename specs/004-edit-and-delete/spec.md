# Feature Specification: 重命名与任务删除的操作入口

**Feature Branch**: `004-edit-and-delete`
**Created**: 2026-11-04
**Status**: Draft
**Input**: 补齐 001 中已实现但没有界面入口的操作：目标、分类、任务的重命名，以及任务删除。

**背景**: `rename_goal`、`rename_category`、`rename_task`、`delete_task` 在存储层均已实现并有测试，但 `src/app` 从未调用它们。结果是名称打错字改不了、任务建错了删不掉，只能改数据库。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 重命名目标与分类 (Priority: P1)

用户在左侧树里对某个目标或分类点「改名」，弹窗预填当前名称，改完提交后左侧树与今日清单的名称同步更新。

**Why this priority**: 名称是唯一的识别手段，不能改名意味着建错一个目标就只能删掉重建，连带丢掉它下面的分类、任务与复习进度。

**Independent Test**: 把目标「学习英语」改为「英语」，左侧树显示新名称；把分类「口语」改为「口语表达」，其下任务不受影响。

**Acceptance Scenarios**:

1. **Given** 一个目标，**When** 点击「改名」并提交新名称，**Then** 左侧树与今日清单都显示新名称，任务与行动不受影响
2. **Given** 同一目标下的两个分类，**When** 把其中一个改名为另一个的名称，**Then** 拒绝并说明重名，弹窗保留
3. **Given** 目标「学习英语」与「日语」，**When** 把「日语」改名为「学习英语」，**Then** 拒绝并说明重名
4. **Given** 重命名弹窗，**When** 输入只含空格或超过上限的名称，**Then** 拒绝并说明原因

---

### User Story 2 - 重命名任务 (Priority: P2)

用户在任务行点「改名」，弹窗预填当前名称，改完提交后任务行与今日清单同步更新。

**Why this priority**: 任务名往往写得更具体，打错字的概率更高；但任务没有唯一性约束，改名不涉及冲突判断，比目标改名简单。

**Independent Test**: 把任务「连读」改为「连读练习」，任务行与今日清单都显示新名称，复习进度不变。

**Acceptance Scenarios**:

1. **Given** 一个任务，**When** 改名为新名称，**Then** 任务行与今日清单同步显示新名称，频率与复习进度不变
2. **Given** 同一分类下两个任务，**When** 把其中一个改成另一个的名称，**Then** 允许（任务名称无唯一性约束）

---

### User Story 3 - 删除任务 (Priority: P1)

用户在任务行点「删除」，系统先说明这条任务还有多少未完成行动会被作废，确认后才删除。

**Why this priority**: 之前只能暂停任务，无法清掉建错的任务；任务会一直占着列表并继续出现在今日清单里。

**Independent Test**: 删除一个今天有未完成行动的任务，确认弹窗显示行动数量，确认后任务从列表消失，今日清单里对应行动变为「已过期」。

**Acceptance Scenarios**:

1. **Given** 今天有未完成行动的任务，**When** 点击「删除」，**Then** 弹窗说明将作废的未完成行动数量，此时尚未删除
2. **Given** 上述弹窗，**When** 确认删除，**Then** 任务从任务列表消失，对应未完成行动显示为「已过期」，待完成数量相应减少
3. **Given** 上述弹窗，**When** 取消，**Then** 任务与行动均不变
4. **Given** 没有未完成行动的任务，**When** 删除，**Then** 弹窗说明将作废 0 条行动，确认后正常删除

---

### Edge Cases

- **改名为原名**：不视为冲突，允许提交且不报错
- **弹窗打开时切换选中的分类**：弹窗内容应保持指向原目标，不应误改到新选中的对象
- **删除正在被今日清单引用的任务**：行动转为「已过期」，不删除已完成行动的历史记录
- **删除后重建同名任务**：任务名无唯一性约束，允许
- **重命名失败后**：弹窗保留、输入内容保留，与新建失败的行为一致

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 目标、分类、任务三类对象 MUST 都能从界面上重命名
- **FR-002**: 重命名入口 MUST 预填当前名称，避免用户重新输入
- **FR-003**: 重命名的名称校验 MUST 与创建一致：去两端空白、拒绝空值与控制字符、限制长度；目标与分类 MUST 继续校验唯一性，任务 MUST 不校验唯一性
- **FR-004**: 校验失败时 MUST 保留弹窗与输入内容，且不修改任何数据
- **FR-005**: 删除任务前 MUST 二次确认，并说明将作废的未完成行动数量
- **FR-006**: 确认删除后，任务 MUST 从列表消失，其未完成行动 MUST 转为「已过期」，已完成行动 MUST 保留
- **FR-007**: 本 feature MUST NOT 修改持久化结构与既有查询语义

### Key Entities

- **改名目标**: 目标 / 分类 / 任务三类对象，共用一套弹窗与校验
- **任务删除**: 软删除任务 + 未完成行动转「已过期」，已有 `delete_task` 实现

## Success Criteria *(mandatory)*

- **SC-001**: 三类对象都能通过界面改名为合法新名称，列表与今日清单 100% 同步
- **SC-002**: 重名或不合法输入 100% 被拒，且被拒后数据不变
- **SC-003**: 删除任务后，该任务 0 次出现在任务列表与今日清单，其未完成行动 100% 显示为「已过期」

## Assumptions

- **任务名不要求唯一**：001 只对目标与分类设了唯一性约束，本 feature 不扩大
- **只做软删除**：任务删除沿用 001 的软删除语义，不做物理删除与回收站
- **不提供批量操作**：一次只改一个、删一个，与现有界面一致
- **不新增确认弹窗样式**：复用删除目标/分类已有的确认弹窗与 `DeletionImpact` 展示方式
