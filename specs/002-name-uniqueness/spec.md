# Feature Specification: 目标与分类名称的唯一性与规范化

**Feature Branch**: `002-name-uniqueness`

**Created**: 2026-11-03

**Status**: Draft

**Input**: User description: "目标名称不能完全相同，同一个目标下的分类名称不能完全相同。目标和分类的名称输入要去除两端空白。"

**修订关系**: 本规格修订 `001-min-action-core` 的 FR-002（分类名称唯一性）与 FR-004（名称校验），其余条款不变。

**Clarifications**:

- Q1 存量重名目标如何处理 → 升级时清空全部业务数据，不做改名或合并
- Q2 「完全相同」的比较口径 → 去除两端空白后比较，英文字母不区分大小写
- Q3 软删除后能否重建同名 → 不能，唯一性覆盖已删除的记录
- Q4 分类重命名是否也查重 → 是，创建与重命名两条路径都校验

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 目标名称唯一 (Priority: P1)

用户已经有一个目标「学习英语」。当他再次创建「学习英语」，或者创建一个仅大小写不同的「Learning English」时，系统拒绝创建并指出与哪个已有目标冲突，原有数据保持不变。把目标重命名为一个已存在的名称同样被拒绝。

**Why this priority**: 目标是三层结构的最外层，重名会让「按目标查看分类」失去唯一入口，用户无法在一堆同名目标中判断该操作哪一个。

**Independent Test**: 从空数据创建一个目标，再次提交同名、大小写变体、两端带空白的变体，全部被拒且列表仍只有一条；再把另一个目标重命名为已存在的名称，同样被拒且名称不变。

**Acceptance Scenarios**:

1. **Given** 已存在目标「学习英语」，**When** 用户再次创建「学习英语」，**Then** 系统拒绝创建，提示与已有目标重名，目标列表不变
2. **Given** 已存在目标「learning english」，**When** 用户创建「Learning English」，**Then** 系统按重复名称拒绝
3. **Given** 已存在目标「学习英语」，**When** 用户创建「  学习英语  」，**Then** 系统按重复名称拒绝
4. **Given** 已存在目标「学习英语」与「日语」，**When** 用户把「日语」重命名为「学习英语」，**Then** 系统拒绝重命名且「日语」名称不变
5. **Given** 已删除目标「学习英语」，**When** 用户创建名为「学习英语」的新目标，**Then** 系统拒绝创建

---

### User Story 2 - 分类名称在同一目标下唯一 (Priority: P1)

用户在「学习英语」下依次建立「语法」「口语」。再次在该目标下建立「口语」时被拒绝；建立仅大小写不同的英文名「Listening」与「listening」同样被拒；在另一个目标下建立「口语」则允许。把分类重命名为同一目标下已存在的名称同样被拒绝。

**Why this priority**: 分类是任务挂载点，同一目标下出现两个同名分类会让用户在添加任务时无法判断往哪个分类里放。

**Independent Test**: 在一个目标下创建分类后重复提交同名（含大小写变体与两端空白变体），全部被拒且分类列表不变；在另一个目标下提交同名分类成功；把分类重命名成同目标下已存在的名称被拒。

**Acceptance Scenarios**:

1. **Given** 目标「学习英语」下已有分类「口语」，**When** 用户在同一目标下再次创建「口语」，**Then** 系统拒绝并说明同一目标下分类名必须唯一，分类列表不变
2. **Given** 目标「学习英语」下已有分类「口语」，**When** 用户在目标「学日语」下创建「口语」，**Then** 创建成功，两个同名分类分属不同目标
3. **Given** 同一目标下已有分类「口语」与「语法」，**When** 用户把「语法」重命名为「口语」，**Then** 系统拒绝重命名且原名称不变
4. **Given** 同一目标下已删除分类「口语」，**When** 用户在该目标下创建「口语」，**Then** 系统拒绝创建

---

### User Story 3 - 名称两端空白被去除 (Priority: P2)

用户输入名称时手滑带上了前后空格，系统保存的是去掉两端空白后的名称，界面回显的也是这个规范的名称；只包含空白的输入被拒绝。

**Why this priority**: 空白差异会绕过唯一性判定，也会让两个看起来一样的名称在列表里并存，属于必须消掉的输入噪音。

**Independent Test**: 输入带两端空白的名称后创建，读取列表与详情，显示的是去空白后的名称；再输入只含空格的名称，创建被拒且不留下数据。

**Acceptance Scenarios**:

1. **Given** 用户输入「  口语  」，**When** 提交创建分类，**Then** 保存并显示的名称是「口语」
2. **Given** 用户输入只含空格的名称，**When** 提交创建，**Then** 系统拒绝并说明名称不能为空
3. **Given** 用户输入「学习 英语」（中间有空格），**When** 提交创建，**Then** 名称原样保留中间空格，与「学习英语」视为两个不同名称

---

### User Story 4 - 旧数据升级后可正常使用 (Priority: P3)

用户升级到新版本后启动程序，旧数据不再保留，程序直接可用并说明数据已清空一次；再次启动不会重复清空。

**Why this priority**: 唯一性约束无法在存量重名数据上直接建立，升级路径必须是确定行为，不能表现为启动失败。

**Independent Test**: 用旧版本数据库启动新版本，程序正常进入今日清单且数据为空；再次启动数据仍为空且不再提示清空。

**Acceptance Scenarios**:

1. **Given** 数据库来自旧版本且含重名目标，**When** 启动新版本，**Then** 业务数据被清空，程序正常进入今日清单
2. **Given** 已经在新版本上运行过，**When** 再次启动，**Then** 不再清空，用户新建的数据保留

---

### Edge Cases

- **大小写变体**：「English」与「english」视为同一名称；「Learn English」与「LearnEnglish」不同
- **空白只在两端**：两端空白不计入名称，名称内部的连续空白原样保留，不做折叠
- **中文与符号**：逐字符比较，不涉及大小写
- **跨作用域同名**：目标名与分类名相同（如目标「口语」下的分类「口语」）允许，二者不在同一作用域
- **软删除后重建**：删除目标或分类后，同名不可重建；此项为 Q3 决策的直接结果，与 001 中「删除后允许重建」的行为不同
- **升级清空失败**：清空过程必须整体成功或整体失败，不得留下部分表已清空的数据库
- **超长与控制字符**：沿用 001 的长度上限与控制字符规则，不受本规格影响

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 目标的名称 MUST 在全部目标记录中唯一，包含已软删除的目标
- **FR-002**: 分类的名称 MUST 在同一目标下的全部分类记录中唯一，包含已软删除的分类；不同目标之间 MUST 允许重名
- **FR-003**: 名称比较 MUST 先去除两端空白，且英文字母 MUST 不区分大小写；中文、数字与符号 MUST 逐字符比较
- **FR-004**: 创建与重命名两条路径 MUST 都执行唯一性校验，目标与分类四类操作无一例外
- **FR-005**: 拒绝重名时 MUST 说明是哪一项输入不合法、与哪一条已有记录冲突、如何修正（改名或先处理原记录），且失败时 MUST NOT 写入任何数据
- **FR-006**: 名称 MUST 在入库前去除两端空白，入库值与界面回显值 MUST 为去除后的值；去除后为空 MUST 拒绝创建或重命名
- **FR-007**: 名称内部的空白 MUST 原样保留，MUST NOT 折叠或规范化
- **FR-008**: 从旧版本数据库升级时 MUST 清空全部业务数据（目标、分类、任务、行动、复习进度、提示状态），保留表结构并记录新的架构版本；已是最新版本时 MUST NOT 清空
- **FR-009**: 升级清空 MUST 在单个事务内完成，失败时 MUST 回滚，不得留下半完成状态

### Key Entities

- **目标**: 名称唯一（全局作用域，含已删除）；名称去两端空白后入库
- **分类**: 名称在同一目标内唯一（含已删除）；跨目标允许重名；名称去两端空白后入库
- **升级动作**: 一次性、整体事务；把旧版本数据库带到新架构版本，业务数据清空

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 所有重名的创建与重命名请求 100% 被拒绝，且被拒后目标、分类、任务的数据条数与名称 100% 保持不变
- **SC-002**: 仅大小写不同的同名输入 100% 被判为重复
- **SC-003**: 带两端空白的名称输入 100% 以去除空白后的值入库并在界面回显
- **SC-004**: 含重名目标的旧数据库 100% 能在升级后正常启动，清空仅发生一次
- **SC-005**: 错误提示 100% 指出重复的名称与冲突对象，用户无需猜测即可完成改名

## Assumptions

- **唯一性覆盖已删除记录**：按 Q3 决策，软删除不再释放名称；这与 001 中分类的部分唯一索引行为相反，属于有意的行为变更
- **大小写不敏感的范围**：仅英文字母参与大小写折叠，中文与其他脚本按原样比较；因此不引入全量 Unicode 折叠
- **清空不提供备份**：升级清空是一次性迁移动作，不做导出、备份或回滚到旧数据的入口；用户如需保留旧数据，须在升级前自行备份数据库文件
- **仅本地单用户**：不存在并发写入竞争，唯一性判定在单进程内即可完成
- **沿用 001 的其他约束**：名称长度上限、控制字符拒绝、界面转义、错误可执行性均按 001 的 FR-004 与 FR-033 执行
- **不改变界面结构**：本规格只改校验与持久化行为，不新增页面、按钮或字段
